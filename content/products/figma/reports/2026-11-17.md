## 执行摘要

**研究截至 2026 年 11 月 17 日。** 本报告覆盖 Figma 官方产品与集成功能，未将社区第三方 AI 插件算作 Figma 自研产品。“已上线”包括正式可用和用户可参与的公开测试，两者分别标注；封闭测试单列，不当成所有人可用。依据公开官网、帮助中心及开发文档，未登录付费账号亲测，不给出生成质量实测分数。

**核心判断：Figma 的 AI 布局已经形成三条主要路线。** Figma Design 的 Agent 面向原生设计资产的生成与修改；Figma Make 面向有代码支撑的交互原型与 Web 应用；Figma Weave 面向图片、视频等内容的多模型工作流。理解三者的产物差异，比把所有能力都叫“AI 画界面”更有用。[官方 AI 总览](https://www.figma.com/ai/)

对产品经理而言，优先研究 Make 如何加速需求验证，Agent 如何利用设计系统与局部上下文，以及 Specs/MCP 如何连接产品意图、设计和代码。视觉创意生产需求强的团队，再深入研究 Weave。以上为基于产品机制的分析建议，不代表效率已经得到本报告实测验证。

## 核心功能与产品定位

| 产品或能力 | 主要输出与用途 | 当前状态 | 需要特别区分的边界 |
| --- | --- | --- | --- |
| Figma Make | 代码支撑的交互原型、Web 应用 | 已正式开放；具体权限依套餐和席位 | 主体可用，不等于所有本地代码库能力全面开放 |
| Figma Design 中的 Figma agent | 生成、修改原生设计，处理设计工作 | 正式可用；2026-10-06 转 GA | 草稿与团队共享文件的编辑权限不同 |
| Figma Weave | 多模型创意素材工作流 | 已上线，有独立产品入口与套餐 | 与 Design 中的 Weave tools 计费池不同 |
| Weave tools in Figma Design | 把封装的视觉工作流用于设计文件 | 2026-10-06 转 GA | 是工具化入口，不等于完整节点编辑器 |
| FigJam AI | 白板、流程图、便签整理等 | 已提供具体功能 | 新的对话 Agent 仍为封闭测试 |
| Figma Slides AI | 演示辅助、讲稿与内容转换等 | 已提供具体功能 | 新的对话 Agent 仍为封闭测试 |
| Figma Sites、Figma Buzz | 网站制作、品牌营销素材生产，内含 AI 工具 | 产品为公开测试 | 产品本身并非完全由 AI 构成 |
| Code layers、Figma Motion、Figma Specs | 画布内运行代码、动画、协作文档 | 公开测试 | 公测和正式版分别评估 |
| Figma MCP server | 让外部 Agent 读取设计或写回原生内容 | 已提供；写画布能力注明 Beta | MCP 提供连接与工具，推理由外部 Agent 承担 |

状态依据：[AI 入门与权限](https://help.figma.com/hc/en-us/articles/23870272542231-Get-started-with-Figma-AI)、[GA 公告与计费变化](https://help.figma.com/hc/en-us/articles/42614902212887-AI-credit-updates-FAQ)、[官方 Beta 清单](https://help.figma.com/hc/en-us/articles/4406787442711-What-Figma-features-are-in-beta)、[MCP 文档](https://developers.figma.com/docs/figma-mcp-server/)。Weave 的持续上线状态另可从其 [更新日志](https://weave.figma.com/change-log)核实。

## 主要特性分析

### 1. Figma Make：让产品想法变成可交互的应用

输入可以是自然语言、已有设计或代码上下文。输出在独立 Make 文件中运行，可通过对话、可视化工具或代码继续调整，并发布为网站。这与生成几张静态界面图的用途不同。[Make 产品页](https://www.figma.com/make/)

更值得关注的新能力是后端：官方目前介绍了由 Payload 支撑的数据库、文件存储、身份认证和管理后台，也保留手动连接 Supabase 的方式。因此，不能再把 Make 概括成“只能生成前端演示”。后端可生成，也不代表权限模型和业务正确性自动通过验收。[后端说明](https://help.figma.com/hc/en-us/articles/32640822050199-Add-a-backend-to-a-functional-prototype-or-web-app)

**适用任务（分析判断）：** 在评审前实现表单、筛选、设置与状态变化，让团队讨论真实操作流程。例如做一个“AI 助手记忆管理”的模拟原型，展示查看、编辑、删除、撤销与失败重试；验证信息结构和操作负担，不需要接入真实用户资料。

**关键限制：** Make 的代码产物不能默认视为结构良好的原生 Figma 图层；复制、转回画布或复用设计资产的具体流程需要验收。生成应用也不能直接替代正式工程中的测试、可维护性和权限审查。

特别注意：官网“本地使用 Make 操作任意代码库”的位置仍有 Coming soon 描述；帮助中心将本地代码库模式列为限量封闭测试。报告不把该模式归入人人可直接使用的主功能。

### 2. Figma agent：在原有画布和设计系统中开展工作

Agent 的关键输入是当前选择的设计对象及附加上下文。用户可要求它生成和修改设计、处理重复任务或给出设计反馈，也能添加设计文件、图片、资料与 skills，并对不同画布对象并行发起任务。[Agent 使用说明](https://help.figma.com/hc/en-us/articles/37998629035799-Work-with-the-Figma-agent-in-design-files)

在共享文件内，Full seat 加编辑权限可以让 Agent 改动文件；Dev、Collab、View 或仅查看权限以询问为主；个人 Drafts 又有不同的试用空间。因而“有 AI 额度”不等于“能修改团队正式设计”。

**与 Make 的核心区别：** 如果目标是让设计师接着编辑组件、布局与矢量，先评估 Agent；如果目标是让用户实际点一遍业务流程，先评估 Make。复杂任务可能需要组合使用，不应只凭首次生成画面是否好看来选工具。

官方客户故事列举了设计系统维护、重复工作与创意表达等用法。这些属于厂商筛选的案例，可用来理解应用方向，不能据此推导普遍效率增益或用户满意度。[官方案例](https://www.figma.com/blog/3-ways-product-designers-use-the-figma-agent/)

First Draft 是需要更新认知的旧名称：其帮助页写明自 2026-05-20 起，Agent 成为这类生成设计功能的新入口。不要再把旧版“First Draft 生成首稿”当成 Figma AI 的全部。[First Draft 说明](https://help.figma.com/hc/en-us/articles/23955143044247-Use-First-Draft-with-Figma-AI)

### 3. Figma Weave：将创意制作过程变成可复用工作流

Weave 使用节点组织生成与编辑过程，将不同模型和专业图像处理工具连接起来。更有价值的对象是可重复执行的生产流程，例如换产品图、换提示词，沿用同一条视觉生产链，而非每次从空白聊天开始。[Weave 官网](https://weave.figma.com/)

官方介绍了分支探索、跨模型比较，以及将流程封装为 Weave tool。Design 中的 Figma frame 也能通过 Figma node 与工作流连接，让设计与素材制作的修改更容易衔接。[Weave 工作流解读](https://www.figma.com/blog/the-tldr-on-figma-weave/)

**适用任务（分析判断）：** 品牌素材变体、统一风格的多组场景图、活动图片与视频制作。对需要经常生成演示素材的产品经理，它的研究价值是“如何固定风格、输入和验收标准”，而不仅是接了多少个模型。

**应验证的边界：** 同一主体跨图片的一致性、局部修改对其他区域的影响、多步骤失败重跑成本、模型替换后流程是否还能稳定复用。这些不能从官网宣传直接判定。

### 4. 日常 AI 工具：小任务覆盖面很广

| 工作类型 | 已有能力示例 | 如何理解它的价值 |
| --- | --- | --- |
| 设计整理 | 语义搜索、图层重命名 | 减少查找与维护成本 |
| 文案处理 | 改写、翻译、语气调整、替换内容 | 让文案贴合具体版式与场景 |
| 图片处理 | 生成和编辑图片、去背景、扩图、移除或提取对象、提高清晰度 | 在设计上下文中处理素材 |
| 矢量素材 | 生成可编辑插画和图标、图片矢量化 | 产物可以继续编辑，不只是位图 |
| 讨论整理 | FigJam 生成白板与图表，聚类和总结便签 | 把会议输入转成可继续协作的对象 |
| 演示制作 | 调整语气、生成讲稿；FigJam 内容转 Slides | 减少整理和转录工作 |

功能分布依据：[AI 工具总表](https://help.figma.com/hc/en-us/articles/23870272542231-Get-started-with-Figma-AI)、[FigJam 功能说明](https://help.figma.com/hc/en-us/articles/16822138920343-Use-AI-tools-in-FigJam)、[矢量生成与编辑](https://help.figma.com/hc/en-us/articles/38031452710807-Generate-and-edit-vectors-with-Figma-AI)。不同产品、席位与文件权限的覆盖范围不同，不是所有按钮在每个产品里都有。

### 5. 公开测试与生态入口：值得关注，但不能混报为全面正式开放

**Code layers：** 在 Figma Design 画布中放入会运行的代码，适合同屏比较交互方案。它与 Make 的关系，可理解为“画布里的行为探索”与“独立应用工作区”。**Motion：** 结合时间线、关键帧与 Agent 辅助制作动画。**Sites 和 Buzz：** 分别面向网站与品牌素材制作，它们内含 AI 能力，但普通编辑、模板与发布也属于其产品价值。以上状态以 [Beta 清单](https://help.figma.com/hc/en-us/articles/4406787442711-What-Figma-features-are-in-beta)为准。

**Specs：** 协作文档可放到画布或白板边上，保存需求、组件说明和技术意图，并让 Agent 生成或修改文档。其产品意义在于为设计和代码提供持续可访问的文字上下文；当前为公开测试。[Specs 指南](https://help.figma.com/hc/en-us/articles/44049066011671-Guide-to-Specs-in-Figma)

**MCP：** 官方服务支持给外部 Agent 提供设计上下文，也介绍了写回原生画布内容、从网页 UI 生成设计层等方向。其中写画布仍标注 Beta，草稿以外的写入还涉及 Full seat；不能假定所有客户端都具备同样能力。[开发文档](https://developers.figma.com/docs/figma-mcp-server/)

**ChatGPT 入口：** Figma 的集成说明目前覆盖 FigJam 图表和 Figma Slides 演示文稿，Slides 集成为 Beta，文档还注明地区限制。不能把“支持 Figma”推演为可在 ChatGPT 中直接生成任何 Figma Design 文件。[集成范围](https://help.figma.com/hc/en-us/articles/35326636109975-Use-ChatGPT-with-Figma)

## 商业模式与定价

Figma 的主体计费模式是“套餐与席位 + AI 用量”。研究日官网显示 Full seat 的月度标价/折算入口分别为 Professional 16 美元、Organization 55 美元、Enterprise 90 美元；后两者明确为年付，Professional 页面有月付/年付切换。本文不把页面默认展示价当成所有账期的价格，税费与实际结算金额未核验。[定价页](https://www.figma.com/pricing/)

| 额度所属计划 | Full seat 每月 AI credits | 备注 |
| --- | ---: | --- |
| Starter | 500 | 同时限制每日 150 |
| Professional | 3,000 | 按账号席位分配 |
| Organization | 3,500 | 可按组织方案补充额度 |
| Enterprise | 4,250 | 具体采购以企业方案为准 |

官网说明个人席位额度按月重置，不结转、不转让；常规 AI 功能共用 Figma AI credits。Agent 与 Make 消耗随任务复杂度变化。AI 搜索、图层重命名和部分便签整理当前列为不消耗积分；**不扣积分不等于免费套餐都有权限使用**。[积分与权限说明](https://help.figma.com/hc/en-us/articles/33459875669015-How-Figma-AI-credits-work)

Weave 独立站有自己的套餐和积分，不能和 Figma AI 的数字直接比较。其定价页同时呈现月度金额和年度账单信息，静态抓取存在账期歧义，因此不将其付费价抄为精确购买报价。已能确认有 Free 及多个付费档位；预算应按所需模型、生成次数与失败重试核算。[Weave 定价](https://weave.figma.com/pricing)

**产品判断：** 采用积分可以把不同模型成本纳入同一消费入口，但也会增加用户对一次任务总成本的不确定感。比单次生成扣了多少分更有用的指标，是一份通过验收的原型或一组可用素材总共花了多少时间与积分。

## 市场分析

### 目标用户画像

1. 产品经理与创业者：需要可交互的需求表达与快速验证，Make 的相关性最高。
2. 产品设计师与设计系统团队：需要在已有组件、变量、品牌规范中修改和扩展设计，Agent 与 MCP 更关键。
3. 品牌、创意与营销团队：需要多尺寸、多风格、多素材的可重复生产，Weave 与 Buzz 更相关。
4. 跨职能协作团队：需要会议输入、需求意图、设计和实现互相衔接，FigJam、Slides 与 Specs 提供相邻入口。

以上为根据功能设计推导的细分用户，不是官方披露的用户规模或付费构成。

### 竞品对比与竞争边界

以下是任务维度的分析，不是未经测试的产品排名，也不宣称各竞品当日支持所有相同能力：

| 任务 | 需要对照的工具类别 | 判断 Figma 是否值得使用的标准 |
| --- | --- | --- |
| 从需求生成可运行原型 | AI 应用构建器、编码 Agent | 是否更好复用已有设计和团队协作上下文 |
| 生成可编辑 UI | AI 原生设计工具、设计编辑器 | 图层、组件与变量是否可维护，修改是否精准 |
| 批量视觉生产 | 多模型创意工作流、图像视频工具 | 品牌一致性与复用流程的收益能否覆盖编排成本 |
| 设计到研发 | IDE Agent、设计交付工具 | 组件映射、上下文获取和返工成本是否下降 |
| 会议到需求 | 白板与文档 AI | 是否保留来源，是否能继续协作并进入下一环节 |

Figma 潜在优势来自既有资产与协作上下文；如果团队没有设计系统、文件维护薄弱，其优势能兑现多少需要实际比较。对只想生成一次性页面的人来说，产品组合的广度也可能成为理解成本。

### 市场口碑与证据边界

本轮搜索可见关于原型效率、输出泛化、设计系统遵循和积分成本的讨论，但未建立有代表性的用户样本。本报告不以零散帖子推导普遍满意度，也不把厂商客户故事当作第三方验证。是否真正省时，需用同一任务比较首稿、修正与交付的总耗时。

## 官网内容洞察

**分析判断一：AI 的中心从按钮集合转向可持续对话的 Agent。** 小工具仍有低门槛价值，但高复杂任务需要在同一上下文中迭代，画布成为任务定位与结果检查的载体。

**分析判断二：Figma 同时经营设计对象和代码对象。** 可编辑设计适合规范维护与协作；可运行代码适合验证行为。Code layers 的出现，使两种对象更容易在同一空间讨论，但不保证两者已实现无损双向同步。

**分析判断三：Specs 是“意图层”，Weave 是“流程层”。** 一个尝试让设计决策持续可读，一个尝试让制作过程可重复。长期价值可能更多来自积累上下文和可复用方法，而不是单次模型输出。

模型策略方面，Figma 官方说明使用第三方与第一方模型组合，并对开放模型做领域后训练；不能将整套产品固定归因于某一个历史模型版本。内容训练设置与启用 AI 也是两个不同议题：官方说明 Starter/Professional 默认开启内容训练、管理员可关闭；Organization/Enterprise 默认关闭。用于公司材料前应核对所在组织的实际设置。[模型与数据使用说明](https://www.figma.com/ai/our-approach/)

## SWOT 分析

| 维度 | 分析判断 |
| --- | --- |
| 优势 | 围绕已有设计、组件、文档与协作关系工作，容易把生成结果接入后续编辑 |
| 劣势 | 产品、席位、权限、积分与 Beta 状态交织，初次理解成本高；总任务成本不够直观 |
| 机会 | 用可运行原型提升 PM 的需求表达，用 Specs 与 MCP 减少意图到实现的信息损失 |
| 威胁 | 通用编码 Agent 和 AI 设计工具持续扩大覆盖面；如果产物返工多，上下文优势未必转化为效率 |

此表为产品机制分析，不是市场份额、财务预测或投资判断。

## 对 AI 产品经理的启发

**把用户操作对象作为上下文入口。** 在设计图上选中组件再提要求，降低了用户描述“改哪里”的负担。迁移到 AI 助手产品，可让用户从一条记忆、一张卡片或一个任务直接发起操作；同时限定变更范围，便于检查和撤销。

**让生成结果进入现有工作对象。** 图层、图表、需求文档和可运行原型都能被继续修改。对多模态记忆而言，也应思考生成内容如何进入可编辑、可追溯、可管理的对象，而不是只留在聊天记录里。

**同时提供单步工具与复杂 Agent。** 确定性强的小任务可直接执行；长任务需要计划、过程可见与结果验收。用一种对话模式覆盖所有任务，未必是最省操作的体验。

**评价完整任务，而非第一次输出。** 建议用以下实验框架开展团队试用，暂不预设分数：

| 评估维度 | 可操作的测量方式 |
| --- | --- |
| 需求覆盖 | 列出必须具备的功能与异常路径，计算实现比例 |
| 编辑性 | 检查组件复用、布局结构、命名与后续人工修改是否顺畅 |
| 局部修改可靠性 | 连续提出 5 次局部修改，记录无关区域受损次数 |
| 交互正确性 | 跑通正常、空数据、加载、错误、撤销等路径 |
| 设计系统遵循 | 抽样检查颜色、排版、组件与变量是否匹配已有规范 |
| 协作与交付 | 让未参与生成的同事继续修改，记录理解成本和返工量 |
| 成本 | 统计到通过验收为止的总耗时、提示轮数与积分 |

建议使用同一份虚构业务 brief，对照手工流程与 AI 流程，先覆盖 3 类任务：从零搭建、基于旧稿修改、复杂状态补全。这样更容易发现工具是在节省首稿时间，还是在降低总体交付成本。

## 结论与建议

对当前的产品工作，建议体验顺序为：**Make 的交互原型 → Design Agent 的局部修改与设计系统使用 → Specs/MCP 的上下文衔接 → Weave 的视觉生产流程。** 这是按产品经理的任务相关性排序，不是质量榜单。

一次有价值的试用可以这样展开：拿一个虚构的 AI 助手设置流程，先生成可操作原型，再要求补充失败重试与撤销，最后交给同事修改。对比“能生成”与“能持续正确修改”之间的差距，比观摩一次漂亮 Demo 更能判断落地价值。
