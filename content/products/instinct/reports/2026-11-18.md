## 执行摘要

**研究日期：2026-11-18。** 本次调研对象为 instinct.com 的个人 AI 助理，与前一份 Second 调研中提到的 Instinct 一致；不涉及同名芯片或其他软件。依据官网、状态页、服务条款、隐私政策及投资方资料，辅以明确标注的媒体信息。未注册、未连接个人账号、未实测订购、通话或消息任务。

**产品判断：Instinct 的核心吸引力是让用户在熟悉的沟通渠道里委托事务，并把执行过程交给 Agent。** 其价值需要以完成结果衡量，而非只看回答内容。它更接近个人事务执行层；Second 更接近为不同 Agent 提供个人背景的一层基础设施，二者并不天然互为替代。

官网的能力描述非常简短，本轮没有找到足以验证完整能力矩阵的官方开发文档。报告因此不将媒体体验、条款许可和所有账号均可稳定使用混为一谈。

## 主要特性分析

### 1. 消息与电话优先的交互入口

官网介绍用户可发消息或打电话，并列举买菜、订火车票、送花及找球场等事务。官方状态页列出 iMessage/SMS、WhatsApp、Email 与网页任务等服务组件。[官网](https://instinct.com/)、[状态页](https://instinct.com/status)

**产品分析：** 这降低了进入门槛，也把 AI 放进用户原有的生活沟通习惯中。但低门槛入口不自动意味着低成本完成任务：当需求不明确、存在多个候选方案或需要核对费用时，纯对话容易产生长串往返。

因此，应该分别评估三件事：用户能否轻松发起任务，Agent 能否持续推进，以及用户能否快速看懂结果。聊天熟悉度主要解决第一件事。

### 2. 从建议跨越到执行

官网强调助理可以使用电话和电脑；现行条款把代用户在第三方服务上进行的操作称为 Actions。这为“执行型个人助理”的产品定位提供了依据，但不证明每个商家、账号或步骤都能成功执行。[官网](https://instinct.com/)、[条款](https://instinct.com/terms)

**任务拆解示例（研究者设计，非实测）：** 用户要求安排周末出行，系统需要获取日期和预算、检索候选、处理可用性、让用户确认必要信息、执行预订，最后交付凭证。途中遇到登录、验证码、缺货或价格变化，都可能阻断执行。

对 Agent 产品，最关键的差别是：用户收到“我替你办好了”时，系统应有可复核的完成证据，而不是只生成一个听起来可信的状态说明。

### 3. 上下文与长期记忆的作用

Instinct 的定位强调理解用户正在做什么、什么重要；隐私政策也说明其服务会记住过去的上下文以辅助请求。公开资料不足以确认其记忆 schema、存储介质、冲突解决、有效期或完整导出方式。[产品页](https://instinct.com/)、[隐私政策](https://instinct.com/privacy-policy)

**研究者判断：** 记忆在这里首先服务于执行。例如订餐时的地点和饮食要求、送礼时的收件人及时间，能减少追问。但同一条记忆并非对所有任务都有效：历史地点、某次临时要求和稳定偏好必须能够区分。

从产品逻辑看，个人 Agent 不只是“有记忆的聊天机器人”，还需要在每次动作前判断：这条记忆现在是否有效，以及是否足以支持行动。这是对产品机制的分析，不是已证实的内部实现。

### 4. 主动式能力的证据边界

部分媒体和用户文章描述了提醒、后台跟进、电话代办等体验，但当前公开官网未给出完整的主动触发规则及覆盖清单。本报告不把“能联系你”推导成“能全天持续观察所有设备并主动办事”。

应区分被动回答、受委托的持续任务、基于规则的提醒，以及自行判断时机的主动建议。它们对可靠性和用户预期的要求不同，不能都用“主动式 AI”一个标签替代。

### 5. 授权与数据使用影响产品可信度

条款要求用户对动作保持监督，且不保证防护机制能阻止所有错误。因此不能假定每个外部动作都会自动逐项请求确认，实际审批体验有待实测。[服务条款](https://instinct.com/terms)

隐私政策允许某些使用信息用于模型训练；退出针对未来且有安全审查例外。Vault 与直接来自 Google Workspace 的数据有特定不训练承诺，不能外推到全部对话。断开一般连接与删除历史数据也并非同一操作，Google Workspace 存在不同处理约定。[隐私政策](https://instinct.com/privacy-policy)

**产品判断：** 这里不仅是设置页问题，也会影响用户愿意接入多少背景。授权越广，Agent 越可能减少追问；用户一旦无法预测数据和动作的边界，就会主动限制信息，进而削弱体验。

## 商业模式与定价

2026-11-17 修订的条款明确说明，Instinct 当前免费，未来可通知用户后引入服务收费。本轮没有核实到公开订阅套餐、调用配额或企业采购价格。免费服务与代用户购买产生的第三方费用应分别理解。[条款 Fees](https://instinct.com/terms)

**商业分析：** 执行型 Agent 的成本可能包含模型、网页操作、电话、等待和失败重试，难以只用消息数估算。未来是否采用订阅、使用量收费或其他方式，不能凭行业惯例替公司宣布。

更有意义的单位经济指标是每个真实完成任务的总成本，并计入未完成任务与人工介入的代价。估值也不能代替这类数据，目前公开材料不足以完成计算。

## 市场分析

### 目标用户画像

**研究者推断：** 首先适合愿意委托日常安排、经常使用国际消息平台、并能提供足够任务背景的用户。生活事务往往跨多个服务，助手的价值在于减少切换与协调，而非提供单一应用已经能完成的操作。

对中国用户，需要额外核实手机号资格、中文电话、境内商家覆盖和现有沟通渠道；本轮没有证据确认支持中国大陆号码、微信或国内各类生活服务。不能因为 WhatsApp/iMessage 入口存在就推断境内任务同样好用。

### 竞品与相邻产品比较

| 对照方向 | 主要交付 | 与 Instinct 的关系及比较重点 |
| --- | --- | --- |
| 普通对话助手 | 建议、内容与信息 | Instinct 强调进入外部服务执行；应比较完成结果而不只比较回答 |
| 单一领域助手 | 某一类事务的稳定服务 | 通用 Agent 覆盖广，但需检验长尾任务是否增加失败和确认负担 |
| 个人上下文层 Second | 可供其他 Agent 使用的个人背景 | 相邻层；Instinct 偏任务执行，Second 偏背景供给，不代表双方已经无缝打通 |
| 自行搭建 Agent | 自选工具、模型及运行流程 | 比较设置和维护成本，以及权限与运行行为的可见程度 |
| 真人助理／礼宾服务 | 协调事务并处理例外 | 价值对照是委托成本、异常处理和结果可追责性，不是聊天拟人度 |

此表是产品机制对比，并不声称所有类别具有相同的功能、价格和可靠性。Second 的定位参考其[官方宣言](https://2.computer/blog/a-model-of-ones-own)。Second 创始人的发布介绍提及 Instinct，但本轮没有独立验证可使用的双方集成接口。

### 市场口碑与体验证据

独立研究文章汇总了早期使用者的正向任务体验与授权、数据保留方面的争议；该文章更新于 2026-09-23，不能直接当成 11 月版本的缺陷清单。[Ry Walker 研究](https://rywalker.com/research/instinct)

本轮未建立有代表性的长期用户样本，未复现特定事故，也不以传播热度推算满意度。评估投诉时需要保留发生日期、账号条件及后续版本变化；评估成功案例则需要计入那些没有完成或需要用户接管的任务。

## 官网内容洞察

**研究者判断一：它把熟悉的人际沟通方式变成任务入口。** 用户不用先找到某个功能菜单，但后台仍需清晰的任务状态管理；入口简单不意味着系统可以省略任务对象。

**研究者判断二：结果比聊天记录更重要。** 可追踪的预订、订单、草稿或取消结果，才是用户真正验收的对象。一次对话结束，不意味着委托结束。

**研究者判断三：用户背景与行动权限需要分别建模。** 知道用户喜欢某种商品，并不等于拥有下单授权；知道某个人是谁，也不等于可以代表用户联系对方。二者如果混在“懂你”这个概念中，会造成难以预料的体验。

**研究者判断四：公开透明度还不足以支撑完整技术评估。** 本轮访问的官方 Blog 显示尚无文章；未找到公开架构图、开发接口或完整工具目录。不能从其他网站给出的笼统介绍，反推具体模型、沙箱实现、加密方案或多 Agent 编排。[官方 Blog](https://instinct.com/blog)

## SWOT 分析

| 维度 | 研究者判断 |
| --- | --- |
| 优势 | 消息与电话入口自然，委托生活事务的价值容易被用户理解 |
| 劣势 | 公开功能与接口资料少，长任务的状态、授权和最终可靠性仍需验证 |
| 机会 | 从给建议进入事务协调与执行，可能创造不同于传统应用点击流程的体验 |
| 威胁 | 原生助手、消息平台和垂直服务都能向执行型 Agent 扩展；第三方服务变化会影响任务成功率 |

## 对 AI 产品经理的启发

### 将聊天入口与任务管理分开

以下为可迁移的产品建议，不是 Instinct 已公开的内部设计。自然语言适合表达目标，结构化任务对象适合管理持续状态。至少应记录目标、约束、所需补充信息、执行阶段、审批状态、失败原因和完成证据。

例如“安排一次出行”不应只有一条完成消息，还应能回答：目前执行到了哪里，费用是否变化，哪些动作已经发生，用户还能否取消。

### 把记忆用于减少追问，不把它当成授权

对车、手机、眼镜等多端助手，可以复用相同任务背景，但按终端能力和用户当下意图决定可执行动作。已知用户偏好只能帮助形成候选，不能替代对执行范围的判断。

这也意味着系统应能识别“只查一下”“先准备”“确认后执行”等不同意图，而不是把所有表达都归成执行任务。

### 主动式体验需要清楚的触发依据

受委托持续跟进的任务、用户设定的提醒、系统根据背景给出的建议，应在产品里有不同的预期。主动联系用户时，最好让用户能理解为什么在此刻出现，以及如何调整这类行为。

### 建议的评估方案

取得访问资格后，可以先用虚构或专门测试数据开展小范围体验。本轮未执行下表实验，不预填通过率。

| 维度 | 测试方式 | 关注指标 |
| --- | --- | --- |
| 任务完成 | 给出明确目标和可验收结果 | 端到端成功率，排除只说成功的情况 |
| 约束遵循 | 设置预算、日期、地点与排除项 | 违反硬约束比例、无谓追问次数 |
| 记忆使用 | 更新一个偏好，再执行相关任务 | 旧值误用、错误归因和背景重复输入量 |
| 局部调整 | 执行前只修改一个条件 | 其他约束保持率及重复执行次数 |
| 审批体验 | 区分查询、准备与执行三种委托 | 过度确认、缺少确认及用户理解程度 |
| 异常恢复 | 模拟缺货、超时、登录失效 | 恢复成功率、接管成本和状态准确性 |
| 后台持续性 | 任务中断后从另一终端继续 | 状态一致性、丢任务和重复动作 |
| 成本 | 记录整个过程而非单次回复 | 总等待、交互轮次和人工维护成本 |

对照方式可采用“自己直接使用应用”“仅让 AI 提供建议”“委托 Agent 执行”三组。只有最后一组在整体成本与正确性上有改善，执行型助理的价值才真正成立。

## 结论与建议

**研究者判断：Instinct 更值得作为消息原生、执行型个人 Agent 的样本研究。** 它让用户以熟悉的方式发起委托，但能否长期成立，取决于异常处理、授权可预测性与完成证据，而非入口是否足够像真人聊天。

如果将它与 Second 一起看，可以得到一个更完整的产品分层：个人上下文帮助系统理解用户，任务系统维护委托状态，执行层完成外部动作，授权和审计贯穿全程。这是设计分析，不是声称两家公司已实现了同一套架构。

当前更合适的下一步，是核实访问资格与具体支持范围，再测试少量明确、可验收的任务。对工作材料和真实外部行动，应依据实际账号配置与组织要求决定使用边界。
