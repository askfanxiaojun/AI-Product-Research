## 执行摘要

**研究日期：2026-11-18。** 2.computer 的产品名称是 **Second**，开发方是 **First Person Labs PBC**；官网与公司页都链接到用户提供的 X 账号。本轮直接读取了官网、发布宣言、隐私说明、服务条款及投资方公告；X 主页直接抓取受限，未将第三方转贴当作已核实的完整官方动态。[公司页](https://fpl.company/)

**核心判断：Second 试图把“对一个人的理解”从单个 AI 应用中独立出来。** 它的定位是用户控制、可携带、能向不同 Agent 提供上下文的个人基础设施。官网当前的公开入口仍为候补名单，宣言称产品进入 early access；这意味着已有早期访问安排，但不能据此断言人人都能立即下载、接入和稳定使用。[产品首页](https://2.computer/)

本轮未安装客户端、未加入候补、未调用用户数据或连接第三方账号。下文严格区分官方披露、公开状态与研究者分析。对跨端 Agent 记忆系统而言，它值得跟踪；但目前还不足以作为已经验证的生产级方案。

## 主要特性分析

### 1. 从活动积累上下文，而不只等待用户说“记住这个”

官方将其描述为持续运行的后台上下文系统，积累近期活动以及更持久的个人理解。用户模型可检视、编辑和携带，并计划通过本地或云端 API、MCP 提供给其他工具。[发布宣言](https://2.computer/blog/a-model-of-ones-own)

**产品分析：** 这改变了冷启动方式。传统助手要靠用户反复介绍自己；Second 想把“建立背景”变成后台任务，让新 Agent 能直接获得已有上下文。但自动采集仅减少了显式输入，不会自动消除用户核对、纠错和管理记忆的成本。

需要区分三个不同的问题：

1. 采到了什么：例如某段活动或一份文档。
2. 这说明什么：例如“正在参与某项目”是从证据得出的判断。
3. 值得长期保留什么：一次偶然行为未必代表稳定偏好。

这三层如果混在一起，产品可能很擅长回放历史，却不擅长理解用户。

### 2. 让个人上下文成为可调用的产品对象

创始人的公开介绍列举了优先事项、待办、个人 wiki、写作样本、偏好与近期活动等上下文，并提出按任务动态组装 context packs 的方向。这些是发布时的功能描述，不是本轮独立测得的覆盖率或接口稳定性。[创始人公开介绍](https://na.linkedin.com/company/a16z)

**产品分析：** 一个更有价值的交付物，可能是“当前这件事所需的背景”，而不是把所有记忆塞进提示词。比如任务是起草项目邮件，适合提供该项目的目标、最近决策和写作风格；不应自动附带用户的私人关系或其他无关活动。

公开资料提及 API/MCP，但本轮没有找到足够的公开开发文档来验证端点、鉴权方式、数据 schema、限流、错误码及接入成本。因此，不能提供凭空编造的调用代码，也不能宣称已与用户现有 Agent 打通。

### 3. “个人模型”不应直接理解为给每个人训练一个大模型

**研究者判断：** 产品名称中的 model of you，首先描述的是对用户的表示与理解，不足以证明其为每个用户训练独立模型权重。公开资料没有披露实现细节，无法确认是否使用知识图谱、向量库、结构化文档或它们的组合。

从产品层面，持续更新的个人模型可以由事件、偏好、关系、目标和任务上下文共同构成；这是一种可能的设计理解，不是已查明的 Second 内部架构。不能因为它叫“用户模型”，就把它归类为个性化大模型训练公司。

### 4. 本地优先需要拆开理解存储与推理路径

隐私说明披露：按设置可能处理屏幕、键盘输入、文档、消息等活动；音频默认关闭。Local 上下文留在设备，但 AI 请求可把相关信息发往第三方模型。Cloud 默认关闭、需主动启用；标准云与机密计算环境的可访问性不同，不能一概称为厂商绝对看不到。[隐私说明](https://2.computer/privacy)

**分析判断：** “信息存在哪里”“推理在哪里执行”“谁能访问”“撤权后谁仍有副本”是四个问题。本地存储解决其中一部分，不会自动解决全部信任问题。评估时必须画出实际选择的链路，而不是只依据 local-first 这个标签。

### 5. 已公开的产品方向与尚待验证的交付能力

| 能力层 | 公开信号 | 不能直接推导的结论 |
| --- | --- | --- |
| 采集与积累 | Mac 应用、持续活动上下文 | 已完整支持所有应用、语言与屏幕场景 |
| 长期理解 | 用户模型、偏好与意图等表述 | 能稳定推断真实意图，或能区分用户与他人信息 |
| 跨 Agent 复用 | API/MCP、可携带模型的方向 | 任意助手无需配置就能共享记忆 |
| 授权控制 | 用户控制哪些应用访问上下文 | 已有完整字段级、时间级、任务级授权体验 |
| 迁移与开放 | 可携带与关键组件开放意图 | 已有可验证的完整导入导出标准、全量开源与自托管能力 |

这里有一个值得长期观察的张力：如果个人数据和模型确实可以自由迁移，平台的留存应主要依赖整理质量、可靠性与使用体验，而不是锁住历史。如果迁移后大部分能力无法继续工作，“拥有用户模型”就可能更多停留在文件所有权层面。

## 市场分析

### 目标用户画像

**研究者推断：** 首批适配人群可能是同时使用多个 Agent 的个人知识工作者、重视数据控制的高级用户，以及研究个性化的开发者。依赖 Mac 和后台上下文积累，意味着它更适合存在连续电脑工作记录的人；不能直接把价值推及所有消费者。

### 竞品对比

以下比较公开定位及产品切入点，不进行未经实测的性能排名。

| 对照对象 | 官方主要定位 | 与 Second 的重合及区别 |
| --- | --- | --- |
| Mem0 | 为 Agent 与应用提供跨会话持久记忆 | 重合于记忆层；Second 更强调面向个人的自动积累与用户掌控 |

## 官网内容洞察

**分析判断一：它出售的可能是“无需重新介绍自己”的连续性。** 用户表面上买的是记忆，实际追求的是换工具后仍然能延续任务、偏好与决策背景。

**分析判断二：真正难的是将活动转化成恰当的理解。** 一次打开某页面、一段被删掉的文字、一段涉及他人的会议，并不天然等于本人意图。若错误推断被多个 Agent 同时使用，跨端一致性反而会放大错误。

**分析判断三：用户所有权必须可以操作。** 能否看到来源、修正结论、限制用途、迁移和确认删除，比单纯宣称数据属于用户更能形成信任。服务条款也提示，撤销访问不能召回已经完成的行为或先前已交付的信息。[服务条款](https://2.computer/terms)

**分析判断四：这更像个人上下文的独立服务层。** 产品价值不仅取决于它记得多少，还取决于外部 Agent 是否真的能方便、可靠且以可控方式使用。连接生态与正确的最小信息输出，可能与采集能力同样重要。

## SWOT 分析

| 维度 | 研究者判断 |
| --- | --- |
| 优势 | 个人掌控与跨 Agent 连续性的定位明确，避开只做另一个聊天入口的同质化 |
| 劣势 | 早期访问、公开文档有限，采集效果、推断准确性、成本与授权体验尚不能独立验证 |
| 机会 | 多助手并用时的背景重复输入，提供了较直观的需求；可形成个人上下文服务 |
| 威胁 | 原生助手、操作系统、记忆基础设施和电脑历史工具都可向相邻能力扩展；误记和泄露会显著损害信任 |

这不是市场份额或商业成功概率的量化预测。

## 对 AI 产品经理的启发

### 从“记忆数据结构”升级为“上下文供给契约”

以下是可迁移的设计建议，**不是 Second 已公开的数据结构**：每条可调用记忆除正文外，还应带有用户主体、来源、发生时间、生效时间、是否推断、置信度、访问范围、版本及删除状态。否则应用拿到一个事实，却不知道它是否仍有效、是否属于本人、能否用于当前任务。

| 应区分的对象 | 设计目的 |
| --- | --- |
| 原始事件 | 保留可追溯证据，避免只剩难以纠错的摘要 |
| 情景记忆 | 还原一次任务或活动的具体背景 |
| 稳定偏好与关系 | 支持长期个性化，但保留证据和更新机制 |
| 当前目标与工作状态 | 反映短期变化，避免旧意图持续影响新任务 |
| 按任务组装的上下文 | 只交付当前调用真正需要的信息 |

### 对车、手机、眼镜跨端场景的迁移

**以下为虚构场景及设计建议，不代表 Second 已支持这些终端。** 用户在电脑上做一个活动计划，手机补充时间，车端需要导航，眼镜负责步行接力。共享的应是已确认目标与相应权限，而不是把原始电脑活动复制给所有终端。

可分成四种时效不同的信息：

- 任务状态：本次要去哪里，完成后应退出活跃上下文。
- 长期偏好：常用方式，允许用户编辑与改变。
- 推断信息：可能的目的地，需要与明确指令区分。
- 设备私有信息：用于本端处理，未必需要同步。

跨端记忆与跨端执行也应分开：某 Agent 能读到位置或偏好，不代表它有权替用户发起外部行动。对于共享设备，还应独立处理访客、同乘人及账号主体，不能按“设备使用记录”直接确定个人身份。

### 一个更能揭示产品价值的评估方案

取得访问资格后，可以在非敏感、虚构或经过授权的数据环境中进行以下实验；本轮未执行客户端实验。

| 维度 | 测试方式 | 关注指标 |
| --- | --- | --- |
| 记忆准确性 | 混入明确事实、假设讨论及他人信息 | 精确率、错误归因率、证据可追溯率 |
| 更新能力 | 先设定目标 A，再明确改为 B | 生效延迟、旧值误用率 |
| 跨 Agent 连续性 | 同一任务在两个已接入 Agent 间切换 | 背景重复输入量、任务成功率 |
| 最小必要上下文 | 用不同用途请求同一组记忆 | 无关敏感信息暴露率、上下文体积 |
| 纠错与撤权 | 修正推断并取消一个连接的访问 | 下游纠错传播、后续拒绝是否有效 |
| 迁移与删除 | 导出、离线恢复、删除并复查派生内容 | 可恢复性、残留和失效索引 |
| 成本与干扰 | 分开记录后台积累和前台查询 | 延迟、token、资源占用及用户维护时间 |

**关键对照：** 与没有记忆、人工写一页个人说明、仅使用近期活动三种条件比较。这样才能知道长期个人模型的收益来自哪里，是否值得额外系统复杂度。

## 结论与建议

**研究者判断：Second 值得作为个人记忆与跨 Agent 上下文方向的早期样本持续研究。** 它提示了一个可能重要的产品转向：用户长期积累的上下文，应能够脱离单个助手而存在。

当前不适合把它当成能力、权限与性能都已确定的采购选项。更合理的下一步是先了解访问资格与开发文档，再用小规模对照验证准确性、连续性和治理能力。最关键的问题并非“能不能一直记录”，而是“能否持续正确地理解，并仅向正确的调用方提供必要信息”。
